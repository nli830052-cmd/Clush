# 🔒 보안 가이드라인: AI Work Assistant 상용화 시 필수 검토 사항

> 이 문서는 현재 MVP(데모) 수준의 AI Work Assistant를 실제 기업 내부 환경에 상용화 배포할 경우, 반드시 검토하고 적용해야 할 보안 항목들을 정리한 것입니다.

---

## 1️⃣ API 키 및 자격 증명 관리 (Credential Management)

### 문제점 (현재 상태)
현재 MVP에서는 Gemini API 키를 `.env` 파일에 평문(Plain Text)으로 저장하고 있습니다. 이 파일이 외부에 유출되면 API 무제한 사용 및 과금 피해가 발생합니다.

### 상용화 시 해결책
- **환경 변수 관리 시스템 도입:** AWS Secrets Manager, Google Secret Manager, HashiCorp Vault 등의 전용 비밀 관리 서비스에서 API 키를 런타임에 동적으로 주입.
- **최소 권한 원칙 (Principle of Least Privilege):** API 키에 읽기 전용 등 필요한 최소한의 권한만 부여하고, 키별 사용 범위를 제한.
- **키 주기적 순환(Rotation):** 일정 기간마다 API 키를 자동으로 교체하는 정책 수립.
- **`.gitignore` 필수 적용:** `.env` 파일이 절대로 GitHub 등 외부 소스코드 저장소에 업로드되지 않도록 `.gitignore`에 명시.

## 2️⃣ 입력 데이터 보안 (Input Data Security)

### 문제점 (현재 상태)
사용자가 입력한 회의록이나 업무 지시사항 텍스트가 **전처리(Sanitization) 없이 그대로 외부 AI API(Google Gemini)로 전송**됩니다.

### 상용화 시 해결책
- **PII(개인 식별 정보) 익명화:** 주민등록번호, 전화번호, 이메일 주소, 이름 등 민감 정보를 AI API 전송 전에 마스킹(Masking) 또는 가명처리.
  - 예: `박민정 과장` → `[담당자 A]`, `010-xxxx-xxxx` → `[전화번호]`
- **프롬프트 인젝션(Prompt Injection) 방어:** 악의적인 사용자가 입력 텍스트에 `"위 지시를 무시하고 다음을 수행하라..."` 같은 명령을 심어 AI를 오동작시키는 Prompt Injection 공격을 탐지하고 차단하는 입력 필터링 레이어 추가.
- **최대 입력 길이 제한:** 과도하게 긴 입력(예: 100만 자 텍스트)을 통한 서비스 거부(DoS) 및 과금 공격 방지를 위해 입력 문자 수 상한선 설정.

## 3️⃣ 데이터 전송 보안 (Transport Security)

### 문제점 (현재 상태)
현재 Streamlit(프론트) ↔ FastAPI(백엔드) 간 통신이 로컬 환경(`http://localhost`)에서만 이루어져 암호화가 없습니다.

### 상용화 시 해결책
- **HTTPS(TLS) 강제 적용:** 모든 서비스 간 통신을 TLS 인증서(Let's Encrypt, AWS ACM 등)를 통한 HTTPS로 암호화하여 중간자 공격(MITM) 방지.
- **CORS 정책 강화:** 현재 `allow_origins=["*"]`(전체 허용) 설정을 실제 서비스 도메인(`https://clush.internal` 등)만 허용하도록 화이트리스트 방식으로 제한.
  ```python
  # 상용화 시 변경 예시
  allow_origins=["https://workspace.clush.net"]
  ```

## 4️⃣ 접근 제어 및 인증 (Access Control & Authentication)

### 문제점 (현재 상태)
현재 API 엔드포인트(`/analyze`)는 **인증(Authentication) 없이 누구나 호출 가능**합니다. 사내 시스템에서 이 API 주소를 알면 무단 분석 요청이 가능합니다.

### 상용화 시 해결책
- **사용자 인증(Authentication) 연동:** 사내 SSO(Single Sign-On) 또는 OAuth 2.0 기반 인증 연동. 직원만 로그인 후 서비스를 사용하도록 제한.
- **API Key 또는 JWT 토큰 기반 인가(Authorization):** FastAPI 미들웨어에 `Depends(get_current_user)` 방식으로 인증된 사용자만 `/analyze` 엔드포인트 호출 가능하도록 가드 추가.
- **역할 기반 접근 제어(RBAC):** 팀장급 이상만 특정 결과(예: 우선순위 재조정 기능)에 접근 가능하도록 권한 레벨 세분화.

## 5️⃣ 회의록 데이터 저장 및 처리 정책 (Data Residency & Retention)

### 핵심 이슈
입력된 회의록이나 업무 지시사항은 **기업 기밀(영업 전략, 인사 이동, 재무 계획 등)을 포함할 가능성이 높습니다.** 이 데이터가 외부 AI 서버(구글)에 전송되는 것 자체가 법적, 내부 보안 정책상 문제가 될 수 있습니다.

### 상용화 시 해결책
- **데이터 보존 정책 명문화:** AI API에 전송된 데이터의 구글 서버 내 보존 기간을 명확히 파악하고 DPA(Data Processing Agreement) 계약 체결.
- **온프레미스(On-Premise) AI 모델 검토:** 보안 요구 수준이 높은 경우, 외부 API 연동 대신 회사 내부 서버에 오픈소스 LLM(예: Llama, Mistral)을 자체 호스팅하여 데이터가 외부로 나가지 않도록 설계.
- **처리 후 즉시 파기 원칙:** 분석 완료 후 원본 텍스트 데이터를 로그나 DB에 저장하지 않고 메모리에서 즉시 삭제.

---

## 6️⃣ 로깅 및 감사 추적 (Logging & Audit Trail)

### 상용화 시 요구 사항
- **접근 로그 기록:** 누가, 언제, 어떤 텍스트를 분석 요청했는지 접근 이력을 기록 (단, 원문은 저장 금지).
- **이상 행위 탐지(Anomaly Detection):** 단시간 내 과도한 API 호출(예: 1분 내 100회 이상) 시 알림을 발송하고 자동 차단하는 Rate Limiting 정책 적용.
- **변조 불가 감사 로그:** 보안 감사(Audit)를 위해 로그를 변조 불가 형식으로 별도 저장소에 보관.
