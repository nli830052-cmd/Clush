## 🏗️ 1. 기술 스택 (Tech Stack) 관련 질문

### Q1. 프론트엔드로 Streamlit을 사용한 이유는 무엇인가요?
**A:** "이번 프로젝트의 핵심 목표는 **빠른 MVP(Minimum Viable Product) 구현과 내부 업무용 프로토타입의 직관적인 데모**였습니다. Streamlit은 파이썬만으로 대시보드 형태의 UI를 즉시 구축할 수 있어 프론트엔드 개발 리소스를 최소화하고 AI 기능 고도화에 더 집중할 수 있었습니다. 또한, Clush WorkPlace와 같은 클라우드 협업 도구의 내부 관리자용 툴 느낌을 연출하기에도 적합하다고 판단했습니다."

### Q2. 백엔드로 FastAPI를 선택한 특별한 이유가 있나요?
**A:** "두 가지 이유가 있습니다. 첫째, **속도와 비동기 처리(Async)**입니다. AI API 호출은 응답 대기 시간이 발생하는데, FastAPI는 비동기 호출을 기본으로 지원하여 서버 자원의 낭비 없이 효율적으로 요청을 처리할 수 있습니다. 둘째, **자동 문서화(Swagger)**입니다. 마이크로서비스 구조에서 프론트엔드와 데이터 형식을 맞추는 것이 중요한데, FastAPI는 Pydantic을 통해 입출력 타입을 엄격하게 검증하고 실시간 API 문서를 제공하여 개발 효율성을 극대화해 줍니다."

### Q3. 왜 Gemini 1.5/2.5 Flash 모델을 선택했나요? Pro 모델이 더 성능이 좋지 않나요?
**A:** "엔터프라이즈 환경에서는 단순히 성능만 좋은 모델보다 **비용 효율성과 응답 속도(Latency)**가 더 중요하기 때문입니다. 회의록 요약과 Task 추출은 비교적 가벼운 추론 작업에 속하며, Flash 모델은 Pro 대비 훨씬 빠르고 저렴하면서도 충분한 정확도를 보여줍니다. 특히 긴 회의록을 처리할 때 context window가 넓은 Flash 계열이 실무에 더 적합하다고 판단했습니다."

## 🛠️ 2. 핵심 기능 및 문제 해결 (Core Features & Solving)

### Q4. '마감 기한 동적 계산' 기능이 왜 중요한가요?
**A:** "AI가 단순히 텍스트 내의 '내일', '금요일' 같은 단어를 그대로 추출하면, 나중에 그 스케줄을 확인하는 사용자는 그게 정확히 언제인지 알 수 없습니다. 이를 해결하기 위해 **프론트에서 회의 일자(기준일)를 입력받아 AI에게 컨텍스트(Context)로 주입**되도록 설계했습니다. 이를 통해 AI가 상대적 시간을 절대적 날짜(YYYY-MM-DD)로 스스로 변환하게 함으로써, 데이터의 신뢰도와 시스템 연동성을 대폭 향상했습니다."

### Q5. 캘린더(.ics) 연동 기능은 어떻게 구현했나요?
**A:** "AI로부터 단순히 텍스트만 받는 것이 아니라, **ISO-8601 포맷(마감기한_iso)**까지 함께 추출하도록 프롬프트를 설계했습니다. 이렇게 얻은 표준화된 날짜 데이터를 바탕으로 프론트엔드에서 iCalendar RFC 표준 규준에 맞는 문자열을 생성하여 `.ics` 파일로 다운로드할 수 있게 했습니다. 덕분에 사용자는 구글 캘린더나 아웃룩 등 어떤 스케줄러와도 즉각적으로 일정을 연동할 수 있습니다."

### Q6. 개발 중 마주친 '404 모델 에러'는 어떻게 해결하셨나요?
**A:** "초기에 사용하려던 특정 모델명이 API 버전에 따라 지원되지 않아 발생한 문제였습니다. 당황하지 않고 `genai.list_models()` 메서드를 호출하여 제 API 키로 현재 접근 가능한 실제 모델 목록을 터미널에서 직접 조회했습니다. 이를 통해 지원 가능한 모델명을 정확히 파악하여 업데이트함으로써 연동 문제를 신속히 해결했습니다."

## 🔒 3. 보안 및 상용화 (Enterprise Security)

### Q7. 실제 회사 시스템에 도입한다면 가장 우려되는 보안 사항은 무엇인가요?
**A:** "가장 큰 이슈는 **기밀 데이터(회의록)의 외부 유출과 API 키 관리**입니다. 이를 해결하기 위해 세 가지 방안을 준비했습니다.
1. **PII 익명화:** 이름, 연락처 등 개인정보를 AI 전송 전에 자체 엔진에서 마스킹 처리합니다.
2. **비밀 관리 서비스:** `.env` 방식 대신 AWS Secrets Manager 같은 클라우드 비밀 관리 서비스를 사용합니다.
3. **온프레미스 LLM:** 보안 요구가 극도로 높을 경우, 외부 API 대신 사내 서버에 Llama3 같은 모델을 직접 호스팅하여 데이터가 외부로 나가는 것을 원천 차단하는 설계를 고려할 수 있습니다."

## 💼 4. Clush(회사)에 대한 열정 및 비전

### Q8. 이 프로젝트가 Clush WorkPlace에 어떻게 기여할 수 있을까요?
**A:** "Clush WorkPlace는 '협업 생산성'이 핵심입니다. 사용자들은 매일 쏟아지는 업무 텍스트 속에서 정작 자신이 무엇을 해야 할지(Action Item) 찾는 데 많은 시간을 낭비합니다. 제가 만든 에이전트는 **비정형 업무 데이터를 정형 데이터로 변환하여 캘린더와 메신저라는 실질적 실행 도구로 매끄럽게 연결(End-to-End)**해 줍니다. 이는 Clush가 추구하는 '초개인화 업무 환경'의 핵심 엔진이 될 수 있다고 확신합니다."

### Q9. 향후 이 프로젝트에 더 추가하고 싶은 기능이 있다면?
**A:** "RAG(Search-Augmented Generation) 기반의 **'과거 이력 연동'** 기능을 추가하고 싶습니다. 오늘의 회의를 지난주 회의록과 대조하여 '지연된 업무'를 자동으로 체크하거나, 담당자의 현재 업무 로드(Job load)를 분석하여 더 정교한 우선순위를 추천해 주는 고도화된 지능형 서비스로 확장하고 싶습니다."
